# 모임 예약 신청 운영

- 신청은 서울 대여 키친의 나라별 요리·문화 모임을 대상으로 한다. 장소·정원·비용은 고정하지 않으며, 일요일과 당일·과거 날짜는 접수하지 않는다.
- `/classes` 및 홈에서 신청 → `inquiries`에 저장 → 운영자 이메일 알림 → 연락해 조건 협의 → 이메일의 운영자 링크에서 확정한다.
- 확정할 때 장소·시간·총비용·최종 메뉴·인원과 신청자 동의 확인을 요구한다. 자동 결제나 자동 확정은 없다.
- 신청자는 완료 화면의 `/reservations#id=…&token=…` 전용 링크로 상태를 확인하고 취소할 수 있다. 토큰은 URL fragment에만 남기고 API 요청 시 Authorization 헤더로 전달한다. 이름·전화번호는 상태 API가 반환하지 않는다.
- 운영자 링크는 비밀 접근 링크다. 메일 전달·공개 게시를 금지한다. 링크 열기(GET)는 상태를 바꾸지 않고, 명시적인 POST만 처리한다. 신청자에게 확정 조건을 직접 안내한다.

## 저장 호환성

기존 `inquiries` 테이블과 RLS를 그대로 사용한다. `name`, `phone`, `preferred_date`, `guests`는 기존 열에 저장하고, `message`에는 `kind: manna-reservation-v1`인 버전별 JSON을 저장한다. 기존 일반 문의는 변환하거나 변경하지 않는다. JSON에는 상태, 나라·음식, 시간대, 요청사항, 확인 토큰의 SHA-256 해시와 확정 안내가 들어간다. 기존 2,000자 제한을 유지한다.

클라이언트 요청 UUID가 기본키이므로 재시도는 중복 생성되지 않는다. 동일 UUID를 다른 확인 토큰으로 재사용하면 거부한다. 확정·취소는 이전 message와 일치할 때만 갱신해 동시에 처리되는 변경의 덮어쓰기를 방지한다.

운영자 링크 토큰은 서버 전용 Supabase 키와 도메인을 분리한 HMAC으로 계산한다. 키가 교체되면 이전 운영자 링크는 무효화된다. 브라우저·로그·응답에 서비스 키나 운영자 토큰을 반환하지 않는다. 별도의 관리자 로그인 없이 현재 운영자 이메일 수신권한으로 접근을 제한한다.

## 환경과 검증

기존 `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`(또는 `SUPABASE_SECRET_KEY`), `RESEND_API_KEY`, `ADMIN_EMAIL`, `RESEND_FROM_EMAIL`을 사용한다. 저장·운영자 알림 설정이 없으면 접수를 준비 중으로 표시한다. 저장 실패는 성공으로 표시하지 않는다. 저장 후 알림 실패는 저장 결과와 구분해 표시한다.

`node scripts/check-reservations.mjs`는 프로덕션 빌드 이후 별도 로컬 저장·메일 서버를 사용해 날짜, 저장, 재시도, 토큰 보호, 운영자 확정, 취소를 검증한다. 실제 고객 자료나 외부 이메일을 사용하지 않는다.

실제 결제는 없으며, 개별 송금이 있었다면 환불·정산은 운영자와 협의한다. 새 회차의 장소·인원·금액을 확정하지 않은 채 운영 중인 정규 회차로 홍보하지 않는다.

## 운영자 전용 대시보드

`RESERVATION_ADMIN_TOKEN`을 서버 전용 Secret으로 설정하면 이메일 서비스 없이 `/admin/reservations#key=…` 전용 링크에서 최근 신청 100건을 관리할 수 있다. 키는 API 호출의 Authorization 헤더로만 전송한다. 공개 메뉴에는 키를 넣지 않는다. 키를 분실하면 서버에서 교체하고 새 전용 링크를 전달한다. 이메일 발송은 Resend가 별도로 설정된 경우에만 수행한다.
